01 / FOLLOW ONE REQUEST

Backend ทำงานอย่างไร?

เส้นทึบคือการเรียกงาน เส้นประคือข้อมูลที่ส่งกลับ MapperถูกเรียกโดยServiceหลังได้Entity ไม่ใช่Databaseส่งDTOให้Controllerโดยตรง

แผนภาพเลื่อนแนวนอนได้บนจอเล็ก · กดกล่องหรือใช้ Tab/Enter เพื่อดู component · การไล่ขั้นเป็นการอธิบายจำลอง ไม่เรียกฐานข้อมูลจริง

โค้ดส่วนนี้ทำอะไร

จำหน้าที่ ไม่ใช่จำแค่ลูกศร: ControllerจัดการHTTP · Serviceจัดการกฎ · RepositoryจัดการSQL · Mapperจัดการรูปร่างDTO · Middlewareจัดการเส้นทางปกติ/ผิดพลาดตามลำดับ
02 / HTTP & EXPRESS

Request อยู่ตรงไหน แล้วใครเป็นคนอ่าน?

ข้อมูลตัวอย่างโค้ดที่อ่าน
Path parameter/products/7req.params.id เป็น "7"
Query parameter?page=2&limit=10req.query.page; validate ก่อนแปลงตัวเลข
JSON bodyPOST/PUT รายละเอียดสินค้าreq.body หลัง express.json()
HeaderContent-Type: application/jsonreq.headers['content-type']

REST ที่ต้องแยกให้ได้

GET อ่าน, POST สร้าง, PUT แทนค่าตาม contract, PATCH แก้บางส่วน, DELETE ลบ Resource ใช้ชื่อคำนาม ส่วน method บอกการทำงาน

Safe: GET/HEAD/OPTIONS มี semantics ว่าไม่ขอเปลี่ยน resource Idempotent: PUT/DELETE ซ้ำแล้วผลสุดท้ายเหมือนครั้งเดียว แต่ status อาจต่าง เช่น DELETE ครั้งแรก204 ครั้งต่อมา404; POST/PATCHไม่รับประกัน

Stateless ไม่ได้แปลว่าไม่มี DB แต่ request ต้องมี context ที่จำเป็น ไม่พึ่งลำดับคลิกของ request ก่อนหน้า

ESM และ async ที่เจอบ่อย

// package.json: "type": "module"
import { getProduct } from './product.service.js';
export async function handler(req, res) {
  const dto = await getProduct(req.params.id);
  return res.status(200).json(dto);
}

async คืน Promise; await รอผล I/O โดยไม่หยุดทั้ง Node process การลืม await อาจทำให้ส่ง Promise แทนข้อมูล งาน CPU หนักยังบล็อก event loop ได้

ลำดับ middleware มีผล: express.json() → router → handler → 404 fallback → error middleware ถ้า middleware ไม่ตอบและไม่ next() request อาจค้าง; /products/search ต้องมาก่อน /products/:id
03 / ONE C · THREE R · ONE U · ONE D

CRUD คือการเดินทางเดิม ที่เปลี่ยนคำถามกับ SQL

ประกาศระบุ 1C/3R/1U/1D แต่ยังไม่บอกว่า Read ทั้งสามเป็นแบบใด เตรียม list, detail, search/filter และ pagination โดยไม่ถือว่าชื่อ resource ตัวอย่างคือข้อสอบจริง

C — สร้าง: body → validate → INSERT → DTO →201

เลือกฟิลด์ที่อนุญาต ตรวจ required/ชนิด/NOT NULL และ unique rule จากนั้น bind ค่า INSERT ใช้ insertIdเฉพาะauto increment แล้วอ่านกลับ ไม่ใช้SELECT MAX(id) หากstringPKให้อ่านด้วยkeyที่clientส่ง

const [result] = await pool.execute(
  'INSERT INTO products (sku,name,brand_id,category,price,ram_gb,storage_gb,color) VALUES (?,?,?,?,?,?,?,?)',
  [sku,name,brandId,category,price,ramGb,storageGb,color]
);
const created = await repository.findProduct(result.insertId);

Precheckไม่กันraceทั้งหมด จึงยังต้องมีDB UNIQUEและmap ER_DUP_ENTRY→409 ไม่ส่ง req.bodyทั้งก้อนลงSQL

R — อ่าน: list / detail / search

Listคืนarray; ถ้าไม่มีข้อมูลยัง200พร้อม[] Detailตรวจnullแล้ว404ก่อนmapper Searchใช้parameter bindingและCOUNTที่มีWHEREเดียวกับรายการ หากLIKEใช้%...%ต้องระบุว่าต้องการwildcardหรือต้องescapeเมื่อค้นหาตัวอักษรตรงตัว

const [rows] = await pool.execute(
  'SELECT id,name,price FROM products WHERE name LIKE ? ORDER BY id LIMIT ? OFFSET ?',
  [`%${name}%`, limit, offset]
);
const [[count]] = await pool.execute(
  'SELECT COUNT(*) AS total FROM products WHERE name LIKE ?', [`%${name}%`]
);
U — แก้ไข: existing → validate → UPDATE → อ่านกลับ

ตรวจว่ามีแถวก่อน หากSKUยังเป็นของตัวเองไม่ถือว่าซ้ำ แต่ถ้าชนกับอีกidต้อง409ตามสเปก ส่งค่าเดิมทุกฟิลด์ยังสำเร็จได้ อย่าใช้changedRows0เป็นnot-found

const existing = await repository.findProduct(id);
if (!existing) throw new AppError('Product not found',404,'PRODUCT_NOT_FOUND');
await repository.updateProduct(id, validatedData);
return toProductDTO(await repository.findProduct(id));

Full-body PUTกับpartial updateต้องแยกให้ชัด ค่า0ห้ามหายเพราะfallbackด้วย||

D — ลบ: existing / affectedRows →204 ว่าง หรือ200ตามโจทย์
const [result] = await pool.execute(
  'DELETE FROM products WHERE id = ?', [id]
);
if (result.affectedRows === 0)
  throw new AppError('Product not found',404,'PRODUCT_NOT_FOUND');
// controller:
res.status(204).end();

WHEREต้องครบ โดยเฉพาะcompositekey ถ้าถูกFKอ้างอิงต้องจัดการ1451ไม่ลบสัมพันธ์อื่นเอง W6กำหนดบางendpointเป็น200+JSON ส่วนW8 DELETE product204ว่าง

อ่านผล mysql2: SELECT → [rows,fields], rows[0]หรือnull · INSERT → result.insertId · DELETE/UPDATE → result.affectedRows; changedRowsกับaffectedRowsต่างกัน และ UPDATEค่าเดิมต้องตีความตามdriver/flags ห้ามเหมารวมว่า0คือ404
04 / ENTITY → DTO

Mapper ทำให้ข้อมูล “ตรงสเปก” มากกว่าตรงตาราง

ก่อนแปลง: Entity

{
  "id": 7, "first_name": "Demo", "last_name": "Student",
  "brand_id": 2, "brand_name": "Sample Brand",
  "price": "1250.50", "internal_cost": "700.00"
}

หลังแปลง: Response DTO

{
  "id": 7, "fullName": "Demo Student",
  "brand": { "id": 2, "name": "Sample Brand" },
  "price": 1250.5
}
const toDTO = e => ({
  id: e.id,
  fullName: `${e.first_name} ${e.last_name}`,
  brand: {id: e.brand_id, name: e.brand_name},
  price: Number(e.price)
});
const listDTO = entities.map(toDTO);

ตัวอย่างnested DTOข้างบนเป็นแนวทางแปลงข้อมูลเมื่อโจทย์ต้องการ ไม่ใช่responseของproductsในWeek08 Request DTOคือallowlistข้อมูลรับเข้า; Response DTOคือallowlistข้อมูลออก SummaryสำหรับlistและDetailสำหรับรายตัวอาจไม่เหมือนกัน

3 จุดที่ต้องระวัง: JOINไม่ตรงalias → fieldหาย · DECIMAL/date/nullต้องตรงชนิดตามcontract · ใช้ {...entity} อาจทำให้internal_cost/password_hashหลุด ค่า0ใช้??เมื่อfallbackเฉพาะnull/undefined
05 / PAGINATION PLAYGROUND

เปลี่ยนหน้า แล้วดู LIMIT / OFFSET จริง ๆ

ตัวอย่างข้อมูล23รายการ ปรับlimitแล้วกดหน้าเพื่อดูว่าแถวไหนถูกข้ามและแถวไหนถูกส่งกลับ นี่เป็นการคำนวณในbrowser ไม่ใช่queryMySQLจริง

สูตรและสิ่งที่ต้องคืน
offset=(page−1)×limit; totalPages=ceil(total/limit) ใช้limitหลังcapแล้วทั้งoffsetและSQL COUNTต้องใช้WHEREชุดเดียวกับSELECT
pageเกินสุดท้ายในโครงนี้ตอบ200กับ[]และtotalจริง; total0ต้องได้totalPages0 ไม่ใช้total||ค่าเริ่มต้นจน0หาย ชื่อsize/limitและtotalItems/totalต้องเลือกตามสเปก
กรณีที่ต้องตรวจ
  • page0/-1/abc/1.5/ค่าว่าง/ซ้ำ → validateก่อนลงSQL
  • limitสูงมาก → rejectหรือcapตามcontract
  • offsetเกินsafe integer → reject
  • ORDER BYต้องแน่นอน ถ้าค่าซ้ำให้มีidเป็นตัวตัดสิน
  • ข้อมูลเพิ่ม/ลบระหว่างเปลี่ยนหน้าอาจซ้ำหรือข้าม ขอบเขตของoffset paginationต้องเข้าใจ ไม่จำเป็นต้องเปลี่ยนเป็นcursorหากโจทย์ไม่กำหนด


06 / FOLLOW THE ERROR
Error เดินย้อนกลับคนละทางกับข้อมูลสำเร็จ
Service throw custom error, repositoryอาจrejectด้วยDB error แล้วPromiseไหลไปExpress5 error middleware หากใช้Express4ให้try/catch+next(err)หรือasync wrapper ไม่catchแล้วกลืนerrorจนrequestค้าง
สถานการณ์HTTPตัวอย่างทำไม
inputผิด / JSONแตก / NOT NULLไม่ครบ400ตรวจได้ก่อนเขียนDB
ค้นidไม่พบ404ไม่เข้าmapperด้วยnull
ER_DUP_ENTRY ·1062409UNIQUE/PKชนกัน
ER_NO_REFERENCED_ROW_2 ·1452400ตามcontractชุดฝึกFKปลายทางไม่มี
ER_ROW_IS_REFERENCED_2 ·1451409resourceยังถูกอ้างอิง
DBล่ม / errorไม่คาดคิด500ซ่อนSQL/stack/credentials
class AppError extends Error {
  constructor(message, status, code) {
    super(message);
    this.status = status;
    this.code = code;
  }
}
// อย่าสลับกับclassที่ใช้statusCode/errorCodeโดยไม่แก้handler
401หมายถึงยังไม่ผ่านauthentication; 403หมายถึงไม่มีสิทธิ์ตามเงื่อนไข; 405คือmethodไม่รองรับ แต่Expressไม่สร้าง405แทน404ให้อัตโนมัติทุกroute 204ไม่มีbody ต้องตั้งHTTPstatusจริง ไม่ใช่แค่fieldในJSON


07 / DATA INTEGRITY
ฐานข้อมูลไม่ได้มีแค่ SELECT / INSERT
Constraint และชนิด key
  • PRIMARY KEYระบุแถว; auto incrementใช้insertId
  • String PKเช่นNA ต้องคงstring ไม่Number/parseInt
  • Composite PKต้องส่งทั้งสองส่วนในWHERE
  • UNIQUEกันชนซ้ำ; NOT NULLบังคับข้อมูล; FKตรวจความสัมพันธ์
  • INNER JOINตัดแถวที่ไม่match; LEFT JOINเก็บฝั่งซ้ายและได้nullเมื่อไม่มีคู่ ต้องmapตามcontract
DELETE FROM product_tags
WHERE product_id = ? AND tag_code = ?;
Transaction ต้องใช้ connection เดียว
const conn = await pool.getConnection();
try {
  await conn.beginTransaction();
  await conn.execute(sqlA, valuesA);
  await conn.execute(sqlB, valuesB);
  await conn.commit();
} catch (error) {
  await conn.rollback();
  throw error;
} finally {
  conn.release();
}
ใช้เมื่อหลายการเขียนต้องสำเร็จร่วมกัน ไม่เรียกpool.queryแต่ละคำสั่งแล้วคาดว่าจะอยู่transactionเดียว และไม่เพิ่มtransactionโดยไม่มีเหตุผลในทุกGET
